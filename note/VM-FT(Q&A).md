VMware FT 常见问题解答

Q: 我们为什么要阅读这篇论文？应该从中学习什么？
A: 阅读该论文的主要原因是它提供了一个清晰的案例研究，展示了通过复制状态机实现容错的方法及其挑战（如确定性、一致性、脑裂问题），这些概念在本学期（包括实验环节）会多次出现。另一个原因是论文结果出人意料：你可能认为在机器指令级别进行复制的代价过高，但作者成功实现了这一机制，其显著优势在于能透明地为现有网络服务器添加容错能力（只要服务器通信负载不高）。

Q: 云服务商是否使用VM FT实现容错？
A: 云服务商确实使用状态机复制技术，但通常是在应用层而非机器指令层实现（后续论文会涉及），以获得更好性能。

Q: 引言提到物理服务器比虚拟机更难保证确定性执行，为什么？
A: 虚拟机更容易确保确定性，因为Hypervisor能模拟和控制硬件行为的诸多方面（例如中断交付的精确时序），这些因素可能导致主备执行差异。

Q: 什么是Hypervisor？
A: Hypervisor是虚拟化系统的核心组件，等同于虚拟机监视器(VMM)。它模拟计算机硬件，客户操作系统及其应用在模拟环境中运行。本文中主备节点都是运行在虚拟机中的客户系统，FT作为Hypervisor的组成部分实现每个虚拟机。

Q: GFS和VMware FT都提供容错，如何选择？
A: FT复制计算过程，可透明地为现有网络服务器添加容错，保持严格一致性且对客户端透明（例如改造邮件服务器）。GFS则专为存储容错设计，因其服务单一（存储），复制效率更高——例如无需在所有副本上同步中断指令。GFS通常是构建完整容错系统的组件之一，而VMware FT本身依赖主备共享的容错存储服务（图1中的共享磁盘），这类服务可用GFS类似方案实现（尽管细节上GFS不完全匹配FT需求）。

Q: 3.4节的反弹缓冲区如何避免竞态？
A: 当网络包或磁盘块到达主节点需写入内存时，若无FT，硬件会在软件执行时直接写入内存。客户指令可能在DMA过程中读取该内存，根据精确时序可能看到或不看到DMA数据（形成竞态）。若主备节点因此产生时序差异（一个在DMA后读，一个在DMA前读），就会导致状态分叉。

FT的解决方案是：在执行期间不直接写入客户内存，而是先将数据拷贝到主节点无法访问的私有"反弹缓冲区"。完成拷贝后，FT Hypervisor中断主节点执行并记录中断点，再将数据从反弹缓冲区写入主内存，最后恢复执行。同时通过日志通道将数据发送给备节点，备节点FT在相同指令点中断执行，写入数据后恢复。这样网络包/磁盘块会在主备节点完全相同的时刻出现，确保内存读取一致性。

Q: 什么是"共享存储上的原子测试设置操作"？
A: 系统使用主备共享的网络磁盘服务器（图1的共享磁盘），该服务器提供"测试设置服务"：维护初始为false的标志位。当主/备节点认为对方故障需要接管时，首先向磁盘服务器发送测试设置操作。服务器执行如下逻辑：
```
test-and-set() {
  acquire_lock()
  if flag == true:
    release_lock()
    return false
  else:
    flag = true
    release_lock()
    return true
}
```
只有当返回true时节点才会接管（"上线"）。高层设计意图是：当主备网络断开时，确保仅一个节点上线。若两者都能连接磁盘服务器，后者将作为仲裁者——测试设置操作只对首个调用返回true。

Q: 遵守输出规则会损失多少性能？
A: 表2显示传输速率会降低，但幅度不大。

Q: 若应用调用随机数生成器，是否会导致主备执行分叉？
A: FT会确保主备获得相同的随机数。所有随机源（如当前时间、硬件周期计数器、精确中断时间）都由Hypervisor控制，拦截相关指令并保证输出一致。

Q: 开发者如何确认捕获了所有非确定性因素？
A: 推测原因包括：(1)作者所在公司拥有精通Hypervisor、微处理器和客户OS内部机制的团队，了解各种技术陷阱；(2)VM-FT借鉴了先前确定性重放项目的日志/重放支持，该项目必然已处理过非确定性源；(3)确定性重放设计者通过大量测试积累了应对非确定性的经验。

Q: 若主节点刚发送输出就故障会发生什么？
A: 备节点接管后会重复输出，导致重复生成。这对网络和磁盘I/O不是问题：网络包的重复会被客户端TCP协议自动丢弃；磁盘I/O具有幂等性（相同数据写入相同位置，且无中间操作）。

Q: 3.4节提到故障时未完成的磁盘I/O需要在备节点上线时重新发起，这些待处理I/O存储在哪里？需要回溯多远？
A: 论文指那些日志中有开始记录但无完成记录的I/O操作。备节点通过检查日志中是否缺失I/O完成中断来判断是否需要重启I/O。

Q: 备节点FT如何在特定指令点（与主节点中断位置相同）交付中断？
A: 多数CPU支持性能计数器功能，FT VMM可设置指令计数，CPU在执行指定数量指令后向VMM发出中断。

Q: 系统安全性如何？
A: 设计假设主备Hypervisor都遵守协议且非恶意（未被攻击者入侵）。系统无法应对Hypervisor被攻破的情况，但能防御恶意或有缺陷的客户OS及应用——FT会忠实地复制这些恶意行为或缺陷。

Q: 仅处理故障停止(fail-stop)是否合理？还有其他故障类型吗？
A: 是合理的，因为现实中的许多故障（如网络/电源故障）本质上是故障停止。更复杂的故障（如计算机看似正常运行但输出错误结果，或恶意攻击导致的故障）属于"拜占庭"故障范畴。课程后期会简要讨论拜占庭容错，但6.824主要关注故障停止。

Q: 既然FT开销低（表1）且易于部署，是否被广泛使用？
A: 不确定，但感觉未达作者预期。在基于开源软件的大型网站领域，人们更多使用应用特定的复制方案。需注意：(1)FT仅支持单核虚拟机，无法利用CPU并行性；(2)表1的日志带宽列显示测试负载I/O压力不大（实际单磁盘/网卡可能产生更大流量）；(3)既然关键状态存储在独立容错共享磁盘中，理论上故障后可从共享磁盘加载状态启动新服务器，数据库崩溃恢复已采用类似机制。

Q: 为何论文说FT不支持多处理器客户机？
A: 多处理器上软件结果取决于指令流的交错方式。要让备节点与主节点同步，FT必须保证两台计算机的交错顺序完全相同，这实现难度很大：既难以探测主节点的交错顺序，也难以控制任一机器的交错。VMware新版本产品通过不同技术（可能是内存快照复制而非操作复制）支持多处理器客户机复制。

Q: 设S1为主节点，S2为备节点。当网络断开后，S2检测到与S1失联并通过测试设置锁成功接管。S1会知道S2已接管吗？是否会出现"脑裂"？
A: S1可能确实不知情，客户端可能继续向其发送请求。但当S1尝试产生输出（给客户端或共享磁盘）时，输出规则要求其等待S2确认所有未完成日志条目。由于S2已不再是备节点（即使能通信）不会响应，因此S1将无法产生任何输出。所以S1自认为仍是主节点并不会实际导致脑裂。这种"无法获得备节点确认就停止服务"的模式常见于复制系统，是预防脑裂的关键机制。
