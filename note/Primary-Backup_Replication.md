    状态机复制
    输出规则
    故障转移/主节点选举

    你可以复制任何应用程序，使用VM FT

目标：高可用性
  即使机器发生故障，也要提供服务
    即使机器发生故障，也不能停机
  方法：复制

复制能处理哪些类型的故障？
  复制适用于单个副本的“故障停止”类型故障
    风扇停止工作，CPU过热自动关机
    有人绊倒副本的电源线或网线
    软件发现磁盘空间不足并停止
  复制可能无法处理错误或操作员错误
    通常不是故障停止
    可能相关（例如某些输入导致所有副本崩溃）
  地震或城市范围的停电呢？
    只有当副本物理隔离时才有用

一种流行的复制方法：复制状态机
  客户端将操作发送给主节点，
    主节点排序并发送给备份节点
  所有副本执行所有操作
    如果起始状态相同，
      操作相同，
      顺序相同，
      确定性，
      则最终状态相同。
（复制的其他方法：状态传输）

VM-FT 使用复制状态机
  实验室也使用
  其他指定的论文也是如此

需要多少副本？
  通常你希望副本少一些，因为多的话成本高
  但要足够多以在修复期间承受故障
    许多系统运行3-5个副本，我们将会看到
  本文仅运行2个副本
    同时可承受1次故障

大问题：
  状态和操作是什么？
  主节点是否必须等待备份节点？
  备份节点如何决定接管？
  在切换时是否可见异常？
  如何让替代的备份节点快速赶上并恢复复制？

我们希望副本在哪一级别相同？
  应用程序状态，例如数据库的表？
    GFS采用这种方式
    高效；主节点只发送高层操作给备份节点
    应用程序必须理解容错
  机器级别，例如寄存器和RAM内容？
    可能允许我们复制任何现有的应用程序而无需修改！
    需要转发机器事件（中断、网络包等）
    需要“机器”修改以发送/接收事件流...

今天的论文（VMware FT）复制机器级别状态
  透明：可以运行任何现有的操作系统和服务器软件！
  对客户端来说就像一台服务器

概述
  [图示：应用程序，操作系统，VM-FT在下方，磁盘服务器，网络，客户端]
  术语：
    超级监视器 == 监视器 == VMM（虚拟机监视器）
    操作系统+应用程序是运行在虚拟机内的“客户”系统
  两台物理机，主节点和备份节点

基本思想：
  主节点和备份节点最初从相同的内存和寄存器开始
    包括相同的软件（操作系统和应用程序）
  大多数指令在主节点和备份节点上执行相同
    例如 ADD 指令
  因此大部分时间，不需要任何工作来保持它们相同！

主节点何时必须向备份节点发送信息？
  每当发生可能导致其执行分叉的事件时。
  任何不是执行指令的确定性结果的事件。

FT必须消除哪些分叉源？
  不是状态函数的指令，例如读取当前时间。
  来自外部世界的输入——网络包和磁盘读取。
    这些表现为DMA数据加上中断。
  中断的时间。
  但不是多核竞争，因为仅单处理器。

为什么分叉会是一场灾难？
  因为备份节点的状态会与主节点不同，
    如果主节点然后失败，客户端会看到不一致。
  示例：6.5840作业提交服务器
    强制执行实验的午夜截止时间。
    硬件定时器在午夜触发。
    让我们用一个*有缺陷的* FT复制提交服务器。
    在主节点上，我的作业包中断在定时器触发*之前*到达。
      主节点会告诉我我的作业获得满分。
    在备份节点上，我的作业在之后到达，所以备份节点认为它晚了。
      主节点和备份节点现在有分叉的状态。
      现在没人注意到，因为主节点回答所有请求。
    然后主节点失败，备份节点接管，课程工作人员看到
      备份节点的状态，显示我提交晚了！
  所以：备份节点必须看到相同的事件，
    相同的顺序，
    在指令流的相同点。

日志通道
  主节点通过网络将所有事件发送给备份节点
    “日志通道”，携带日志条目
    中断、传入的网络包、从共享磁盘读取的数据
  FT从日志条目为备份节点提供输入（中断等）
  FT抑制备份节点的网络输出
  如果任何一个节点停止能够通过网络相互通信
    “上线”并提供唯一服务
    如果主节点上线，它停止向备份节点发送日志条目

每个日志条目：指令编号，类型，数据。

FT处理定时器中断
  目标：主节点和备份节点应该在指令流的完全相同点看到中断
  主节点：
    FT处理定时器中断
    FT从CPU读取指令编号
    FT在日志通道上发送“在指令编号X处的定时器中断”
    FT将中断传递给主节点，并恢复它
    （依赖CPU支持将中断定向到FT软件）
  备份节点：
    忽略自己的定时器硬件
    FT在备份节点到达指令编号X之前看到日志条目
    FT告诉CPU在指令编号X处将控制权转移给FT
    FT模拟备份节点看到的定时器中断
    （依赖CPU支持在第X条指令后跳转到FT）

FT处理网络包到达（输入）
  主节点：
    FT配置NIC将包数据写入FT的私有“缓冲区”
    在某个时刻包到达，NIC执行DMA，然后中断
    FT获取中断，从CPU读取指令编号
    FT暂停主节点
    FT将缓冲区复制到主节点的内存中
    FT在主节点中模拟NIC中断
    FT将包数据和指令编号发送给备份节点
  备份节点：
    FT从日志流中获取数据和指令编号
    FT告诉CPU在指令编号X处中断（到FT）
    FT将数据复制到客户内存中，在备份节点中模拟NIC中断

为什么需要缓冲区？
  我们希望数据在主节点和备份节点执行的确切相同点出现在内存中。
  因此如果它们在中断前读取包内存，它们看到相同的内容。
  否则它们可能会分叉。

FT VMM模拟本地磁盘接口
  但实际存储在一台网络服务器上——“共享磁盘”
  所有文件/目录都在共享存储中；没有本地磁盘
  只有主节点与共享磁盘通信
    主节点将其读取的块转发给备份节点
    备份节点的FT忽略备份应用程序的写入，从主节点的数据中提供读取
  共享磁盘使得创建新备份更快
    不需要复制主节点的磁盘

备份节点必须滞后一个日志条目
  假设主节点在指令编号X处获得中断
  如果备份节点已经执行过了X，那就太晚了！
  所以备份FT不能执行，除非至少有一个日志条目在等待
    然后它只执行到那个日志条目中的指令编号
    并在恢复之前等待下一个日志条目

示例：非确定性指令
  有些指令即使主节点/备份节点具有相同状态也会产生不同结果
  例如读取当前时间或处理器序列号
  主节点：
    FT设置CPU以在主节点执行此类指令时产生中断
    FT执行该指令并记录结果
    将结果和指令编号发送给备份节点
  备份节点：
    FT读取日志条目，为指令编号设置中断
    FT然后提供主节点获得的值，不执行指令

关于输出（发送网络包，写入共享磁盘）呢？
  主节点和备份节点都执行输出指令
  主节点的FT实际执行输出
  备份节点的FT丢弃输出

输出示例：数据库服务器
  客户端可以发送“递增”请求
    数据库递增存储值，回复新值
  所以：
    [图示]
    假设服务器的值初始为10
    网络将客户端请求传递给主节点上的FT
    主节点的FT通过日志通道发送给备份节点
    FT将请求包传递给主节点和备份节点
    主节点执行，将值设置为11，发送“11”回复，FT实际发送回复
    备份节点执行，将值设置为11，发送“11”回复，FT丢弃
    客户端获得一个“11”响应，正如预期

但等等：
  假设主节点发送回复然后崩溃
    所以客户端获得“11”回复
  AND日志通道丢弃带有客户端请求的日志条目
    主节点已死，所以不会重新发送
  备份节点上线
    但它内存中的值是“10”！
  现在客户端发送另一个递增请求
    它将再次获得“11”，而不是“12”
  糟糕

解决方案：输出规则（第2.2节）
  在主节点发送输出（例如发送给客户端，或写入共享磁盘）之前，
  必须等待备份节点确认所有先前的日志条目

再次，使用输出规则：
  [图示]
  主节点：
    接收客户端“递增”请求
    在日志通道上发送客户端请求
    即将发送“11”回复给客户端
    首先等待备份节点确认先前的日志条目
    然后发送“11”回复给客户端
  假设主节点在此序列中的某处崩溃
  如果在主节点收到备份节点的确认之前
    可能备份节点未看到客户端请求，也未递增
    但主节点也不会回复
  如果在主节点收到备份节点的确认之后
    然后客户端可能看到“11”回复
    但备份节点保证收到了带有客户端请求的日志条目
    所以备份节点将递增到11

输出规则是一件大事
  以某种形式出现在大多数强一致性复制系统中
    通常称为“同步复制”，因为主节点必须等待
  对性能的严重限制
  是应用程序特定的聪明才智领域
    例如可能不需要主节点在回复只读操作之前等待
  FT没有应用程序级别的知识，必须保守

Q：如果主节点在收到备份节点的确认后立即崩溃，
   但在主节点发出输出之前呢？
   这是否意味着输出将永远不会生成？

A：备份节点在发送回复包给客户端的指令之前或之后上线。
   如果在之前，它将发送回复包。
   如果在之后，FT将已丢弃该包。但备份节点的
     TCP会认为它已发送，将期待一个TCP ACK包，并且
     如果没有收到ACK将重新发送。

Q：但如果主节点在发出输出后崩溃呢？
   备份节点是否会第二次发出输出？

A：可能会！
   对于TCP是可以的，因为接收方忽略重复的序列号。
   对于写入共享磁盘也是可以的，
     因为备份节点将相同的数据写入相同的块号。

切换时的重复输出在复制系统中相当常见
  客户端需要保留足够的状态以忽略重复项
  或者设计成重复项无害
  VM FT“免费”获得重复检测，
    TCP状态在备份节点上由VM FT复制

Q：FT是否能应对网络分区——是否可能遭受脑裂？
   例如如果主节点和备份节点都认为对方已死。
   它们都会上线吗？

A：共享磁盘服务器打破平局。
   磁盘服务器支持原子的测试和设置。
   如果主节点或备份节点认为对方已死，尝试测试和设置。
   如果只有一个存活，它将赢得测试和设置并上线。
   如果两者都尝试，一个将失败，并停止。

共享磁盘服务器需要可靠！
  如果磁盘服务器宕机，服务也宕机
  他们考虑的是一个昂贵的容错磁盘服务器

Q：在恢复过程中备份节点崩溃会发生什么？

A：没有主节点也没有备份节点来接管。系统将
宕机，直到集群服务启动了一个新虚拟机。

Q：为什么不支持多核？

性能（表1）
  FT/非FT：令人印象深刻！
    几乎没有减慢
  日志带宽
    直接反映磁盘读取速率 + 网络输入速率
    最大18 Mbit/s
  我觉得日志通道流量数字似乎偏低
    应用程序可以以每秒数百兆比特的速度读取磁盘
    所以他们的应用程序可能不太依赖磁盘

什么时候FT会吸引人？
  关键但低强度的服务，例如名称服务器。
  软件不方便修改的服务。

高吞吐量服务的复制呢？
  人们使用应用程序级别的复制状态机，例如数据库。
    状态只是数据库，而不是所有内存+磁盘。
    事件是数据库命令（put或get），而不是包和中断。
    可以为只读操作提供快捷方式。
  结果：更少的日志流量，更少的输出规则暂停。
  GFS使用应用程序级别的复制，Lab 2等也是如此
